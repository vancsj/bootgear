# Required confirmation checkpoints

Accept only model confirmation or source-skill selection for the current task.
Reject routine design decisions, goal sign-off and requests for mutation permission from this mode.
Reuse the current run, task folder and advisor pairings. Never call session init.

For models, show user expectations and limits, then concepts, responsibilities, relations and boundaries.
Name the uncertainty or material change. Clear, unchanged models need no new question.
Check whether an existing user confirmation covers the exact payload and scope.

For sources, show each candidate and its proposed scope. Keep phases and orchestration within the user's scope.
Offer invoke, absorb without invocation, or neither. Do not infer a selection from availability or deputy advice.
Ask again only when the skill or scope changes beyond the existing confirmation.
Record confirmed values with `user-message` or `user-confirmed-ledger-entry` references.
Only after confirmation may the caller use deputy's public recording workflow, where available.

Use the host interaction tool when confirmation is still required.
Without interaction, return needs-confirmation with the complete pending payload. Do not draft affected specs or record a source-dependent pass.
On a missing interaction capability, return unavailable with its actual diagnostic.
Return confirmation or clarification to the author. Recheck changed models before affected drafting.
Apply user-requested run amendments only through the existing amendment contract. This checkpoint grants no permission.
